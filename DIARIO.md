## 2026-11-08
- Divisão de trabalho: a implementação ficou com o agente (Claude Code) e eu fiquei com o levantamento e a escolha das ferramentas, a direção e a revisão. A Parte 3 foi delegada com harness pesado (skills de regras de código, segurança e TDD adaptadas de um projeto Laravel meu).
- Adaptei as skills de Laravel para NestJS/React. Um conflito apareceu logo: a skill de segurança manda "404, nunca 403" para acesso indevido, mas o enunciado pede para demonstrar o 403. Resolvi assim: papel errado → 403, corrida de outro passageiro → 404 (ver DECISIONS.md).
- Decidi não versionar o PDF do enunciado num repositório público.
- O Docker não subia de jeito nenhum. Meu primeiro palpite foi a BIOS, mas o Windows dizia `VirtualizationFirmwareEnabled: True`. O `wsl --status` reclamava da falta da "Plataforma de Máquina Virtual", e o `wsl -d Ubuntu` falhava com `HCS_E_SERVICE_NOT_AVAILABLE`. O serviço `vmcompute` nem existia. A causa: eu tinha desligado esses recursos do Windows para rodar o BlueStacks, um emulador Android incompatível com Hyper-V. Lição: quando o Docker no Windows falhar, olhar primeiro `wsl --status` e o serviço `vmcompute`, não a BIOS.
- Ao reativar o recurso, o `dism /enable-feature` entrou em loop de download (`DownloadProgress 0/100 → 50/100 → 0`, visto no `CBS.log`). Havia um reboot pendente (`RebootPending`) e o serviço BITS estava parado. Precisou de reboot no meio.
- O `npm install` trouxe o TypeORM 1.1.2 (major recém-lançada). Fixei em 0.3.31: num desafio com prazo, prefiro a linha que conheço e que tem documentação madura.
- No lint, o `recommendedTypeChecked` do typescript-eslint acusou `no-unsafe-*` em todos os testes, por causa do `res.body` do supertest, que é `any`. Relaxei essas regras só em `test/**` e `*.spec.ts`; no código de produção elas continuam valendo.
- O template novo do Vite liga `erasableSyntaxOnly`, que não aceita parameter properties (`constructor(public readonly status)`). Troquei por campo explícito.
- O `npm audit` acusou DoS no `multer` 2.4.0 (high), dependência transitiva do `@nestjs/platform-express`. Subir o Nest para 11.2.8 não resolveu, porque ele ainda fixa o multer 2.4.0. Resolvi com `overrides` para 2.5.0. Não usamos upload, mas o CI falha em high por política.
- No KEDA, o `TriggerAuthentication` apontava para `corridas-secrets`, mas o `secretGenerator` gera o nome com hash (`corridas-secrets-g2c4h72kbh`), e o kustomize não conhece esse CRD. Descobri renderizando com `kubectl kustomize`. Resolvi com um `nameReference` em `kustomizeconfig.yaml`.
- Rodei o code review do Claude Code no diff inteiro. Ele achou 10 pontos e corrigi 7. O mais sério: uma publicação de evento perdida deixaria o GET mostrando status velho por 1h (TTL), e agora a API grava o cache no PATCH. Também: backoff de 1s fixo mandava evento válido para a DLQ numa queda curta do Redis; motorista via o status da corrida alheia na mensagem do 409; a UI ficava presa em 422 depois de editar o form.
- Ao escrever um teste unitário do backoff, o Jest quebrou com `Must use import to load ES Module` em `@nestjs/config`. O npm tinha trazido a linha 12 desses pacotes (ESM-only) com o core 11 (CJS). Em runtime o Node 24 carrega via require(esm), por isso o build passava, mas qualquer e2e quebraria. Alinhei tudo na linha 11 e o amqp-connection-manager na 4.x. Lição: `npm install pacote` sem versão num ecossistema que acabou de mudar de major é pedir problema.
- Como o Docker local continuou sem a Plataforma de Máquina Virtual, usei o GitHub Actions como laboratório. Criei o repositório privado e só vou abrir depois do CI verde. Na primeira rodada, os e2e da API passaram de primeira e os do worker falharam com `Missing required sub-document 'driver' in the client metadata document`: o driver mongodb 7.8, instalado sem versão fixa, não fecha o handshake com o servidor Mongo 7. Fixei o driver na 6.x. Depois os 6 testes passaram, mas a suíte ainda falhava com `Unhandled error`: a sonda do `beforeAll` fazia `checkQueue` numa fila inexistente, o broker fechava o canal com 404 e o amqplib emitia `error` sem listener.
- Criei um job no CI que sobe o compose inteiro e roda o roteiro do README, e ele achou dois bugs que nenhum teste unitário ou e2e pegaria: (1) API e worker morriam no boot com `PORT has failed isInt`. Campo sem anotação de tipo (`PORT = 3000`) faz o `emitDecoratorMetadata` registrar `Object`, e o class-transformer não converte `"3000"`; os e2e não viam porque usam os defaults. (2) Corrigido isso, a API subia mas ficava `unhealthy`: o `wget localhost` dentro do `node:24-alpine` resolve para `::1` primeiro e a app escuta em `0.0.0.0`. Troquei para `127.0.0.1`. Lição: testar o artefato do jeito que ele vai ser usado (`docker compose up`) pega uma classe de erro que teste de código não pega.
- O k6 no CI deu 8.568 requisições, 0 falhas e p95 de 62 ms. A surpresa veio do `docker stats`: a API chegou a 330 MiB com o OpenTelemetry ligado, e o limit de 256Mi que eu tinha posto no Kubernetes ia causar OOMKill. Recalibrei os resources com os números medidos.
- Um commit só de documentação fez o e2e do worker falhar (`condição não satisfeita a tempo` no primeiro teste via broker). Como o código não tinha mudado, era teste instável, e não fui rodar de novo até passar. Causa: o setup esperava a fila existir, mas o worker declara a fila antes do bind com a exchange; uma mensagem publicada nesse intervalo fica sem rota e é descartada. Agora o setup espera `consumerCount >= 1`, que só acontece depois do bind.
- O `kubectl` sumiu do PATH depois do reboot, porque ele vem do Docker Desktop. Usei o caminho completo em `C:\Program Files\Docker\Docker\resources\bin`.
